# От «вероятного» маршрута к точному

Чего не хватает ytraceroute для построения 100% маршрута и какие **минимальные**
изменения в yggdrasil-go / ironwood это закрыли бы. Архитектурный анализ;
никаких изменений в коде не предлагается выполнить — только описание.

Анализ проведён по состоянию репозиториев на 2026-11-16:

| Репозиторий | Версия |
|---|---|
| yggdrasil-go | `d832d02` (после 0.5.15) |
| ironwood | `0712ecc` — совпадает с пином в `go.mod` yggdrasil-go |
| ytraceroute | текущий `main` |

Ссылки на код ниже — относительно корней соответствующих репозиториев.

## 1. Как на самом деле решается маршрут

Маршрут пакета до `dest` — это последовательность вызовов
`_lookup(path, watermark)` ([ironwood/network/router.go:701](https://github.com/Arceliar/ironwood/blob/0712ecc/network/router.go#L701))
на каждом транзитном узле X. Каждый вызов требует **четырёх** входов, и все
четыре живут только в памяти X:

1. **Вид дерева X** (`infos`: key → parent) — CRDT-срез дерева, по которому
   `_getDist` считает treespace-дистанцию каждого пира *в системе координат
   корня X* (router.go:676–699, `_getRootAndPath` — router.go:641).
2. **Стоимость линков X** (`lags`) — EWMA RTT на каждый `*peer`;
   `_getCost` = целые миллисекунды, минимум 1 (router.go:226–233;
   обновление EWMA — router.go:435–454).
3. **Тай-брейки `prio` / `order`** — при равном `cost·dist` побеждает меньший
   `dist`, затем меньший `cost`, затем старейший линк (router.go:731–772).
4. **Полный список пиров** — `peers map[publicKey]map[*peer]struct{}`:
   на один ключ может быть несколько физических линков (TCP + TLS и т.п.).

Выбор: среди пиров строго ближе к `dest`, argmin `cost·dist` с тай-брейками.
Плюс watermark: каждый хоп обязан быть строго ближе предыдущего.

Watermark ytraceroute реплицирует честно (`src/walk.rs`: строго убывающий
дистанц — та же семантика, что router.go:705–711).

## 2. Гэп-анализ: чего не хватает

| # | Вход `_lookup` | Что отдаётся наружу сегодня | Чем подменяет ytraceroute | Цена подмены |
|---|---|---|---|---|
| ① | `infos`-вид X (parent/root) | `debug_remoteGetTree` отдаёт **только ключи** — родитель выбрасывается в `yggdrasil-go/src/core/proto.go:217`, хотя `DebugTreeInfo` (ironwood `network/debug.go:37`) его содержит; локальный `gettree` (api.go:111) отдаёт полные записи | координатами, выученными **нашим** узлом через `getPaths` | dist посчитан в чужой системе координат: другой корень / несинхронный CRDT-срез → кандидат может быть оценён неверно |
| ② | `lags` → cost | **не отдаётся вовсе** (локальный `getpeers` знает `Cost`; удалённый — нет) | константой 1 мс | argmin `cost·dist` вырождается в argmin `dist`: реальный линк 5 мс на дистанции 1 проигрывает линку 1 мс на дистанции 2 — и наоборот |
| ③ | тай-брейки `prio`/`order` | не отдаются (в `DebugPeerInfo` их нет) | детерминированным «наименьший ключ» | полный тай (равные cost·dist, dist, cost) решается иначе, чем на реальном узле |
| ④ | полный список пиров | `debug_remoteGetPeers` — голые 32-байтные ключи, обрез по MTU (~2000), порядок — случайный порядок итерации map (proto.go:169–181) | «unknown peers» → флаги доверия `?`/`†` | у гигантского хаба ближе-находящийся пир может просто не попасть в ответ |
| ⑤ | **одномоментность** | — | walk собирает данные секунды | реальный пакет проходит все `_lookup` за миллисекунды; `infos` дрейфует (maintenance раз в секунду, router.go:94–105), `lags` плывёт (EWMA) → предсказание — смесь временных срезов, пакет видит один |

## 3. Варианты изменений (по возрастанию вмешательства)

### 3.1 Вариант A — «оракул решения»: `debug_remoteGetNextHop` ⭐ рекомендуется

Не реплицировать решение X, а **спросить у самого X**. Один новый debug-тип
поверх существующего overlay-транспорта:

- **ironwood**: метод `Debug.Lookup(path) (nextKey, selfDist)` в
  `network/debug.go` — `phony.Block(&router)` + вызов `r._lookup`
  (≈15 строк; сам `_lookup` не трогается).
- **yggdrasil-go**: одна пара request/response в `proto.go` по образцу
  `sendGetTreeRequest` (≈40 строк) + регистрация в `SetAdmin`.

Walk превращается в: `path = pathfinder.paths[dest].path` (уже есть у
ytraceroute из `getPaths`) → спросить у X «твой next hop и новый watermark?» →
перейти к ответу.

**Все пять гэпов закрываются конструктивно**: узел решает своим живым `infos`,
своими `lags`, своими тай-брейками, без обрезки и без рассинхрона срезов.
Одномоментность — ровно такая же, как у реального пакета: пакет тоже сэмплирует
состояния последовательных узлов в разные микросекунды.

### 3.2 Вариант B — «полные данные»: расширить два существующих ответа

Данные **уже есть** в структурах — удалённые handlers их просто выбрасывают:

- `_handleGetPeersRequest` (proto.go:169): записи
  `key(32B) + cost(varint) + prio(1B) + n_links` вместо голых ключей —
  закрывает ②③④.
- `_handleGetTreeRequest` (proto.go:213): полные записи `key + parent + seq` —
  закрывает ①: ytraceroute сможет вычислять `_getDist` **в системе координат
  X**, включая проверку совпадения корней (router.go:682–685).
- Мелочь в ironwood: относительный `order` в `DebugPeerInfo`.

Реплика `_lookup` в `src/routing.rs` получает точные входные данные.
Остатки: скью времени между двумя RPC (порядка maintenance-такта, ~1 с) и
обрезка дерева у хабов (~680 записей по 96 байт на MTU). Изменения — только
в yggdrasil-go (proto.go), почти нулевой риск.

### 3.3 Вариант C — «настоящий traceroute»: record-route проба в ironwood

Новый wire-тип `wireProtoPathTrace` в семействе `pathLookup` / `pathNotify` /
`pathBroken` (ironwood `network/pathfinder.go`): источник шлёт пробу к dest с
watermark; каждый хоп делает `_lookup`, **дописывает свой ключ** в
ограниченный список (≤64) и форвардит; dest или узел-тупик возвращает запись
источнику — паттерн обратной маршрутизации уже реализован в
`_handleBroken`/`pathBroken` (pathfinder.go:238–253).

Единственный вариант, дающий 100% маршрут **конкретного пакета в конкретный
момент** (включая шорткаты и моменты перестроек). Показательно, что автор сам
муссирует source-route идеи в комментарии router.go:19–37.

### 3.4 Сравнение

| | A — оракул | B — полные данные | C — record-route |
|---|---|---|---|
| Точность | точное решение узла на момент запроса | точные входные данные (скью между RPC) | точный маршрут фактического пакета |
| Изменения в ironwood | ~15 строк (`Debug.Lookup`) | ~5 строк (`order` в `DebugPeerInfo`) | ядро: wire-тип + handler (~100–150 строк) |
| Изменения в yggdrasil-go | ~40 строк (proto.go) | ~30 строк (proto.go) | ~40 строк (admin-команда) |
| Требует апгрейда | опрашиваемых узлов | опрашиваемых узлов | **каждого транзитного узла на пути** |
| Что получает ytraceroute | замену walk на цепочку запросов | точную репликацию своего walk | один вызов на направление |

**Рекомендация**: A как ядро (самый компактный, ни одной строки в горячем
пути); опционально cost в `remoteGetPeers` из B — почти бесплатно, сохраняет
возможность объяснять «почему» (альтернативы, запасы по стоимости). C — если
цель не инструмент, а upstream-фича честного traceroute для всех.

## 4. Вариант C: распределение по слоям

### Почему ядро обязано быть в ironwood

`debug_remote*` ездит в end-to-end зашифрованной сессии (`typeSessionProto`) —
туда можно положить только диалог «источник ↔ destination». Record-route проба
должна выполняться **транзитными узлами**: каждый хоп дописывает свой ключ и
форвардит. Это wire-уровень между пирами — территория ironwood. Код
yggdrasil-go физически не может перехватить форвардинг на чужом узле.

### Что где лежит

| Слой | Что добавляется | Объём |
|---|---|---|
| **ironwood** (все узлы сети) | константа `wireProtoPathTrace` в iota-блоке (wire.go:10–17); один `case` в диспетчере (peers.go:293–301); структура + encode/decode рядом с pathLookup/pathNotify/pathBroken; `_handleTrace`: lookup → дописать ключ → форвард, у dest — развернуть обратно по координатам источника (семантика pathBroken); API-крючок для инициатора | ~100–150 строк |
| **yggdrasil-go** (узел-инициатор) | admin-команда `debug_trace <key>`: отправить пробу, дождаться ответа, отдать JSON — по образцу `getTreeHandler` (proto.go:335) | ~40 строк |
| **ytraceroute** | вместо walk — один вызов admin-сокета на направление | упрощение |

### Кто шлёт пакеты — отдельный бинарник не нужен

Проба должна исходить от участника сети (у него есть пиры, дерево, `infos`),
поэтому её шлёт **локальный yggdrasil-демон** по команде клиента. ytraceroute
(или `yggdrasilctl debug_trace …`) просто дергает admin-сокет — как сегодня
дергает `debug_remoteGetPeers`. Standalone-бинарнику всё равно пришлось бы
встраивать ironwood целиком (как делает yggstack) — а тогда он сам узел сети,
и библиотека даёт ему это бесплатно.

### Развёртывание

Диспетчер ironwood на неизвестном wire-типе молча дропает пакет
(`default:` в peers.go:301). Поэтому:

- A/B требуют апгрейда только **опрашиваемых** узлов;
- C требует апгрейда **каждого транзитного узла** — до этого проба тихо
  исчезнет на первом старом хопе.

Жизненный цикл: C как upstream-фича в ironwood + yggdrasil-go, ytraceroute на
переходный период делает гибрид — пробует `debug_trace`, при таймауте
откатывается к предсказанию (наличие новой версии на узле проверяется через
`getNodeInfo`, который ytraceroute и так умеет).

## 5. Безопасность и приватность

### 5.1 Базовая линия: что уже не приватно

- **Транзитные узлы уже видят ключи источника и назначения каждого пакета.**
  Заголовок `traffic` на router-уровне открытый: `source`, `dest`, path,
  watermark (ironwood `network/traffic.go:9–16`); шифруется только payload
  (session-слой поверх). Хоп всегда знал: «через меня идут пакеты от A к B».
- **Топология уже полностью собираема любым участником**: `debug_remote*`
  не имеют ACL — любой узел может удалённо собрать списки пиров и вид дерева
  всех остальных. ytraceroute это и эксплуатирует.
- **pathLookup уже мультикастит «кто кого ищет»** по дереву через
  bloom-фильтры (pathfinder.go:60).
- Что Yggdrasil реально защищает: **контент** (e2e-шифрование), **привязку
  ключа к IP** (ниже router-слоя), **неучастников** (узел вне пути пакет
  не видит в принципе).

### 5.2 Вариант A — нейтрален, местами лучше статус-кво

- **Класс информации не меняется**: next-hop для dest — та же топология,
  что уже восстановима через существующие RPC. Оракул отдаёт даже *меньше*
  данных, чем вариант B: только результат, без кандидатов и стоимостей.
- **Нагрузка / DoS**: один запрос = один `_lookup` = стоимость форварда
  одного пакета. Для сравнения, нынешний ytraceroute на каждый хоп устраивает
  fanout проб, каждая из которых поднимает network-wide bloom-мультикаст
  lookup. Оракул снижает генерируемый шум на порядки; при желании — тот же
  throttle, что у pathfinder (`pathThrottle`).
- **Пассивная наблюдаемость**: ничего нового — запрос ездит в сессии, как
  существующие `debug_remote*`.

### 5.3 Вариант C — одно критичное дизайн-правило

**Что становится точнее:** инициатор получает точный список хоп-ключей своего
маршерта. Но «источник всегда мог трассировать свой маршрут» — и сегодня,
приближённо и шумно. Класс информации тот же, точность выше.

**Правило: trace только от себя.** Возврат записи должен идти по координатам
*инициатора* и приниматься только если `source == self` — ровно семантика
приёма `pathBroken` (pathfinder.go:245). Если правило нарушить (разрешить
подставной `source`), появится новая способность, которой сегодня нет: узел E
сможет картировать путь **между произвольными** A и B. С правилом E может
трассировать только E→B — как ICMP-traceroute: со своей машины можно, за
других — нет.

Остальное — не хуже статус-кво:

- видимость пробы хопами = видимость любого пакета между теми же точками;
- неучастники — C даже мягче: проба уникастится по жадному пути, без
  мультикаста, узлы вне пути не дёргаются;
- амплификация O(1): запрос ~100 байт, ответ ≤64 ключа (~2 КБ), каждый хоп
  форвардит один раз; замкнутость от петель наследуется от watermark;
- перехват возврата по координатам совпадает с фундаментальной слабостью
  жадной маршрутизации по coords, о которой автор пишет сам (router.go:19–37):
  перехватить ответ сможет лишь тот, кто и так способен перехватывать любой
  трафик к инициатору — нового вектора нет;
- destination может молча дропнуть пробу (как nodeinfo/lookup) — трасса
  просто таймаутится;
- новый wire-тип = новая поверхность парсинга, но структура в том же
  фуззируемом семействе encode/decode и ограничена по размеру.

### 5.4 Сводная таблица

| | A | C |
|---|---|---|
| Контент / key↔IP / анонимность конечных точек | незатронуто | незатронуто |
| Скрытность топологии от участников | её и не было | её и не было (точность ↑) |
| Шум в сети (side-channel для наблюдателей) | ↓ тише, чем сегодня | ↓↓ тише, чем сегодня |
| Новый вектор | нет | только при нарушении правила «trace from self» |

**Вывод:** приватность не теряется — в обоих случаях раскрывается только то,
что модель угроз Yggdrasil никогда не считала секретом (топология для
участников, маршрут для его собственной конечной точки). C требует дисциплины
в одной строчке семантики (`source == self` на приёме ответа) — единственное
место, где неаккуратность создала бы реальную утечку.

## 6. Фундаментальный предел

Даже при идеальной реализации остаётся физический предел: трассировка и
реальный пакет — **разные события во времени**; дерево может перестроиться
между ними, а маршрутизация ≠ доставка (очереди, дропы). Это предел самой
задачи (ICMP-traceroute в интернете имеет то же свойство), а не архитектуры.
